# Feature Specification: PixiJS 游戏框架

**Feature Branch**: `001-pixijs-game-framework`
**Created**: 2026-04-11
**Status**: Draft
**Input**: User description: "基于 PixiJS 实现一个游戏框架，包含资源生命周期管理（加载/卸载/debug preview 等）、场景管理、UI 分层、跨平台实现（Web/微信小游戏/抖音小游戏）。优先使用 PixiJS 生态成熟库（UI、Layout、AssetPack、Spine 等），模块支持热拔插以实现包体最小化。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 搭建最小可运行项目 (Priority: P1)

作为一个游戏开发者，我希望通过安装框架核心包并配置少量代码，就能启动一个包含画布和基本渲染循环的项目，以便快速开始游戏开发。

**Why this priority**: 框架的安装和初始化是所有后续功能的前提，如果不能在几分钟内跑起来，开发者会直接放弃。

**Independent Test**: 安装核心包后，仅用 10 行以内的代码即可启动一个显示"Hello World"的空白画布，并能正常响应窗口缩放。

**Acceptance Scenarios**:

1. **Given** 一个空的 npm 项目, **When** 开发者安装框架核心包并调用初始化函数, **Then** 页面出现一个全屏画布，显示默认背景色，无报错
2. **Given** 框架已初始化, **When** 开发者修改窗口大小, **Then** 画布自动适配新的窗口尺寸
3. **Given** 框架已初始化, **When** 开发者卸载所有非核心模块, **Then** 核心包体积不超过 50KB（gzip 后）

---

### User Story 2 - 资源加载与管理 (Priority: P1)

作为一个游戏开发者，我希望通过统一的接口加载、缓存、预览和卸载各类资源（纹理、精灵表、Spine 动画、音频等），以便高效管理游戏中的各类素材。

**Why this priority**: 资源管理是游戏开发的基础能力，直接影响加载体验和内存占用，几乎所有游戏都需要。

**Independent Test**: 开发者可以加载一张纹理并显示在屏幕上，随后通过调试工具预览该资源的状态，最后卸载它并验证内存已释放。

**Acceptance Scenarios**:

1. **Given** 框架已初始化, **When** 开发者调用资源加载接口加载一组纹理, **Then** 资源按优先级顺序加载，并通过回调报告加载进度（0-100%）
2. **Given** 资源已加载完成, **When** 开发者打开调试面板, **Then** 可以看到所有已加载资源的列表、类型、内存占用和引用计数
3. **Given** 资源已加载且无引用, **When** 开发者调用卸载接口, **Then** 资源从内存中释放，GPU 纹理被销毁，调试面板同步更新
4. **Given** 正在加载大量资源, **When** 加载过程中发生网络错误, **Then** 单个资源失败不影响其他资源加载，失败的资源标记为错误状态并支持重试
5. **Given** 资源清单已配置, **When** 开发者使用 AssetPack 打包资源, **Then** 资源按配置自动分块加载，首屏仅下载必要资源

---

### User Story 3 - 场景管理与切换 (Priority: P1)

作为一个游戏开发者，我希望通过简洁的 API 定义多个游戏场景（主菜单、战斗、地图等），并在场景间平滑切换，以便组织游戏内容。

**Why this priority**: 场景管理是游戏架构的核心骨架，没有它，游戏将是一堆无序的渲染逻辑。

**Independent Test**: 开发者定义两个场景并注册到框架中，通过一行代码触发切换，验证旧场景的资源被正确清理、新场景的资源被正确加载。

**Acceptance Scenarios**:

1. **Given** 框架已初始化且注册了多个场景, **When** 开发者调用场景切换接口, **Then** 当前场景执行退出流程（保存状态、播放退出动画），然后新场景执行进入流程（加载资源、播放进入动画）
2. **Given** 场景切换需要加载较多资源, **When** 加载耗时超过 300ms, **Then** 框架自动显示内置 Loading 提示，加载完成后过渡到新场景
3. **Given** 场景 A 切换到场景 B, **When** 切换完成, **Then** 场景 A 独有的资源被自动卸载，共享资源保留在缓存中
4. **Given** 场景切换正在执行, **When** 开发者再次触发切换, **Then** 第二次切换被排队或拒绝，不会导致状态混乱
5. **Given** 场景使用了 Spine 动画, **When** 场景切换离开, **Then** Spine 资源随场景一起释放

---

### User Story 4 - UI 分层与布局 (Priority: P2)

作为一个游戏开发者，我希望在游戏画面之上叠加 UI 层，并使用灵活的布局系统排列 UI 元素（按钮、列表、弹窗等），以便构建美观的游戏界面。

**Why this priority**: UI 是几乎所有游戏的刚需，但可以在场景管理之后实现，因为 UI 本质上是场景的组成部分。

**Independent Test**: 开发者在游戏画面之上创建一个包含按钮和文本的 UI 面板，验证 UI 始终显示在游戏内容之上，且正确适配不同屏幕尺寸。

**Acceptance Scenarios**:

1. **Given** 框架已初始化, **When** 开发者创建 UI 层并添加按钮、文本等组件, **Then** UI 元素始终渲染在游戏内容之上，不受游戏缩放影响
2. **Given** UI 层已创建, **When** 屏幕尺寸变化, **Then** UI 元素根据布局规则自动重新排列（如弹性布局、锚点定位）
3. **Given** UI 层使用了 PixiJS Layout 库, **When** 开发者不安装该模块, **Then** UI 功能优雅降级，不影响其他功能正常运行
4. **Given** UI 层存在多个面板, **When** 开发者配置层级关系, **Then** 面板按配置的 z-index 正确叠加显示

---

### User Story 5 - 模块热拔插与按需加载 (Priority: P2)

作为一个游戏开发者，我希望在项目配置中声明需要的功能模块（Spine、AssetPack、UI 等），未声明的模块完全不打包进最终产物，以便实现最小包体。

**Why this priority**: 跨平台发布（尤其是小游戏平台）对包体大小有严格限制，模块可裁剪是核心卖点，但需在基础架构稳定后实现。

**Independent Test**: 开发者创建两个配置——一个包含所有模块，一个只包含核心模块——对比两个产物的体积差异，验证非核心模块可完全裁剪。

**Acceptance Scenarios**:

1. **Given** 框架核心已安装, **When** 开发者在配置中不包含 Spine 模块, **Then** 最终构建产物中不包含任何 Spine 相关代码
2. **Given** Spine 模块已安装但代码中未引用, **When** 构建项目, **Then** Spine 模块被自动裁剪，不出现在最终产物中
3. **Given** Spine 模块已安装但代码中未引用, **When** 开发者将其标记为不可裁剪, **Then** 该模块仍保留在最终产物中
4. **Given** 项目配置了 Spine 模块, **When** 开发者移除该配置, **Then** 项目编译通过，仅核心功能可用，Spine 相关 API 不可调用
5. **Given** 所有可选模块均未配置, **When** 构建项目, **Then** 产物体积仅包含框架核心（渲染引擎适配 + 场景管理 + 资源管理）
6. **Given** 某个可选模块已配置, **When** 该模块的依赖库未安装, **Then** 框架在启动时给出明确的错误提示，指出缺少的依赖

---

### User Story 6 - 跨平台适配 (Priority: P2)

作为一个游戏开发者，我希望同一套游戏代码能在 Web、微信小游戏和抖音小游戏平台上运行，只需修改入口配置而非业务逻辑，以便最大化游戏覆盖面。

**Why this priority**: 跨平台是框架的重要价值，但每个平台的适配器可以独立开发，不影响核心架构设计。

**Independent Test**: 开发者编写一个包含场景切换和资源加载的示例游戏，分别在 Web 和微信小游戏平台上运行，验证行为一致。

**Acceptance Scenarios**:

1. **Given** 游戏代码已编写完成, **When** 开发者为 Web 平台构建, **Then** 生成标准的 HTML + JS 产物，可在浏览器中运行
2. **Given** 游戏代码已编写完成, **When** 开发者为微信小游戏平台构建, **Then** 生成符合微信小游戏规范的目录结构，可直接上传到小游戏后台
3. **Given** 游戏代码已编写完成, **When** 开发者为抖音小游戏平台构建, **Then** 生成符合抖音小游戏规范的目录结构，可直接上传
4. **Given** 游戏代码使用了窗口适配 API, **When** 在不同平台上运行, **Then** 画布自动适配平台窗口尺寸，无需平台特定代码
5. **Given** 游戏需要存储数据, **When** 在不同平台上调用存储 API, **Then** 框架自动映射到平台对应的本地存储实现

---

### User Story 7 - 调试与开发工具 (Priority: P3)

作为一个游戏开发者，我希望在开发模式下获得可视化的资源监控面板和场景调试工具，以便快速定位性能问题和资源泄漏。

**Why this priority**: 调试工具显著提升开发效率，但不影响生产环境功能，可在核心功能稳定后迭代。

**Independent Test**: 开发者启动调试模式后，在屏幕上看到实时帧率、资源内存占用和当前场景层级树。

**Acceptance Scenarios**:

1. **Given** 框架以开发模式运行, **When** 开发者打开调试面板, **Then** 显示实时 FPS、内存占用、已加载资源列表和场景层级树
2. **Given** 调试面板已打开, **When** 开发者点击某个资源, **Then** 显示该资源的详细信息（类型、大小、引用计数、加载时间）
3. **Given** 调试面板已打开, **When** 存在资源泄漏（引用计数不为零但已标记卸载）, **Then** 面板以警告色高亮显示该资源
4. **Given** 框架以生产模式构建, **When** 构建完成, **Then** 调试面板相关的所有代码被完全裁剪

### Edge Cases

- 当资源在加载过程中被卸载请求打断时，框架应取消加载并释放已下载的部分数据
- 当场景切换过程中发生未捕获异常时，框架应回退到安全状态（如错误提示场景），而不是黑屏
- 当可选模块的运行环境不满足（如 WebGL 不可用）时，框架应给出明确的降级提示
- 当在小游戏平台上首次加载超过平台包体限制时，框架应自动触发分包下载策略
- 当多个模块同时请求同一资源时，框架应合并请求，避免重复加载
- 当 WebGL 上下文丢失后自动恢复时，如果某些资源无法重建（如动态生成的纹理），框架应标记这些资源为异常状态并通知业务层

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 框架 MUST 提供统一的初始化接口，一行代码完成渲染引擎和核心模块的启动
- **FR-002**: 框架 MUST 以 npm monorepo 形式发布，各功能模块为独立 npm 包，通过 tree-shaking 实现按需引入
- **FR-002a**: 构建工具 MUST 自动裁剪代码中未实际引用的模块，即使其在 package.json 中声明为依赖；MUST 提供显式标记机制（如配置项）将指定模块标记为不可裁剪
- **FR-003**: 框架 MUST 使用 PixiJS Assets 作为资源加载的基础设施
- **FR-004**: 资源管理模块 MUST 支持资源的加载、缓存、引用计数、卸载完整生命周期
- **FR-005**: 资源管理模块 MUST 集成 AssetPack 支持资源的分块打包和按需下载
- **FR-006**: 资源管理模块 MUST 在开发模式下提供可视化调试面板，展示资源状态和内存占用
- **FR-007**: 场景管理模块 MUST 支持场景的定义、注册、切换和生命周期回调（enter/exit/suspend/resume）
- **FR-008**: 场景切换 MUST 支持过渡动画（淡入淡出、自定义过渡等）；当资源加载耗时较长时，MUST 显示内置的 Loading 提示，开发者可自定义 Loading 场景外观
- **FR-009**: 场景切换 MUST 自动管理场景级资源的加载和卸载
- **FR-010**: UI 模块 MUST 支持在游戏画面之上创建独立的 UI 渲染层
- **FR-011**: UI 模块 MUST 基于 PixiJS Layout 实现弹性布局系统
- **FR-012**: UI 模块 MUST 支持常用 UI 组件（按钮、文本、列表、弹窗、滚动容器等）
- **FR-013**: 框架 MUST 提供平台适配层，抽象窗口创建、资源路径、本地存储、输入事件等平台差异
- **FR-014**: 框架 MUST 支持 Web 平台作为默认平台
- **FR-015**: 框架 MUST 支持微信小游戏平台适配
- **FR-016**: 框架 MUST 支持抖音小游戏平台适配
- **FR-017**: Spine 动画模块 MUST 作为可选模块，通过配置启用
- **FR-018**: 未启用的可选模块 MUST 完全不包含在最终构建产物中（零体积开销）
- **FR-019**: 框架 MUST 支持响应式画布适配，自动处理不同分辨率和 DPR
- **FR-020**: 框架 MUST 在生产模式下完全裁剪调试工具代码
- **FR-021**: 框架 MUST 自动处理 WebGL 上下文丢失事件，重建 GPU 资源并恢复渲染状态，完成后发出事件通知业务层

### Key Entities

- **GameApplication**: 框架主入口，负责初始化渲染引擎和协调各模块
- **Module**: 功能模块的抽象基类，各模块为独立 npm 包，通过 tree-shaking 实现按需引入
- **AssetManager**: 资源管理器，封装加载、缓存、引用计数和卸载逻辑
- **AssetRef**: 资源引用句柄，携带引用计数和资源元信息
- **Scene**: 游戏场景，定义 enter/exit/suspend/resume 生命周期
- **SceneManager**: 场景管理器，处理场景注册、切换、过渡动画
- **UITier**: UI 分层容器，管理 UI 元素的层级和布局
- **PlatformAdapter**: 平台适配器，抽象窗口、存储、路径等平台差异
- **DebugOverlay**: 调试覆盖层，显示资源状态、FPS、场景树等调试信息

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 开发者能在 5 分钟内完成从安装到运行一个可交互的示例项目
- **SC-002**: 核心框架（不含可选模块）的 gzip 后体积不超过 50KB
- **SC-003**: 仅启用核心模块的项目构建产物比全模块项目减少 60% 以上体积
- **SC-004**: 同一套游戏代码在 Web、微信小游戏、抖音小游戏三个平台上的行为差异不超过视觉像素级别
- **SC-005**: 加载 100 张纹理的资源管理操作（加载/卸载）不导致帧率低于 55 FPS
- **SC-006**: 场景切换的过渡动画期间帧率不低于 55 FPS
- **SC-007**: 90% 的框架 API 有完整的类型定义和文档注释

## Clarifications

### Session 2026-04-11

- Q: 框架的发布形态是什么？ → A: npm monorepo 多包发布，各模块独立 npm 包，通过 tree-shaking 实现按需引入
- Q: "模块热拔插"的具体含义是什么？ → A: 自动按引用裁剪，即使 package.json 中声明了依赖，若代码未实际引用则自动剥离；支持显式标记模块为不可裁剪（强制保留）
- Q: 框架目标对齐哪个 PixiJS 大版本？ → A: PixiJS v8（最新主推版本，新 Assets 系统，更好的 ESM 支持）
- Q: WebGL 上下文丢失时如何处理？ → A: 自动恢复 + 事件通知：框架自动重建资源并恢复渲染状态，完成后通知业务层
- Q: 场景切换过程中的加载体验如何设计？ → A: 内置过渡动画 + 可选 Loading 状态，框架提供默认过渡和 Loading 提示，开发者可自定义 Loading 场景外观

## Assumptions

- 开发者使用 TypeScript 作为主要开发语言
- 项目使用现代构建工具（Vite 或类似）进行打包，需支持 ES Module tree-shaking
- 目标浏览器支持 WebGL 2.0，不支持的环境降级到 Canvas 2D
- 微信小游戏和抖音小游戏平台支持 WebGL 渲染
- PixiJS 的 `@pixi/ui`、`@pixi/layout`、`@pixi/assetpack`、`@pixi/spine-pixi` 等包已足够成熟可用于生产
- 框架基于 PixiJS v8 构建，利用其全新 Assets 管理器和 ESM 原生支持
- 开发者熟悉 PixiJS 的基本概念（Application、Container、Sprite 等）
- 小游戏平台的包体限制为微信 20MB / 抖音 16MB（首包），框架设计应支持分包策略
- 资源的引用计数采用手动管理加可选的自动垃圾回收策略
- 框架不负责音频管理（超出当前范围），但预留音频模块的扩展点
